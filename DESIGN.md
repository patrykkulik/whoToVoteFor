# WhoToVoteFor — Design (Revised)

## Goal

A clean, fast, mobile-first web app that helps UK voters discover which party best matches their views. Users answer a Likert-scale survey of policy statements; results show a ranked match against the Big 6 parties, **grounded in their 2024 General Election manifestos** with mechanically-verified citations.

The system has two halves:

1. **Runtime app** — a static Next.js site, fully client-side, LLM-free, deterministic.
2. **Build-time pipeline** — an offline tool that ingests manifesto PDFs and emits the data file the runtime reads. The pipeline uses an LLM, but every output it produces is mechanically verified and gated through a human review step before being committed.

This separation is deliberate: the running website never calls an LLM, never makes a fabricated claim possible, and is auditable from a single TypeScript file.

## Non-Goals

- No backend, no accounts, no analytics of individual responses (privacy-first).
- No live aggregation of "how others answered" in v1.
- No constituency-level tactical-voting advice in v1.
- No LLM at runtime — automation lives entirely in the build-time pipeline.

## Tech Stack

### Runtime app

| Concern | Choice | Reason |
|---|---|---|
| Framework | **Next.js 15 (App Router) + TypeScript** | SEO landing page, file-based routing, static-export friendly. |
| Styling | **Tailwind CSS v4** + CSS variables | Fast, consistent, easy dark mode. |
| UI primitives | **shadcn/ui** (Radix) | Accessible primitives without heavy deps. |
| Animation | **Framer Motion** via `LazyMotion` + `domAnimation` | Smooth transitions, lazy-loaded to keep bundle small. |
| Charts | **Hand-rolled SVG bar chart** (one component, ~50 lines) | Avoids ~90KB Recharts/d3. There is only one chart. |
| State | **Zustand** + persist middleware (with safe-storage wrapper) | Simple, hydration-safe. |
| Validation | **Zod** | Schema for the manifesto data file at module load (dev) and in CI. |
| Icons | **lucide-react** | Tree-shaken. |
| Tests | **Vitest** (unit) + **Playwright** (1 e2e) | Light but production-credible. |
| Hosting | **Vercel** (canonical), with static export as a verified secondary target | Both built in CI. |

### Build-time pipeline (separate workspace, not shipped to client)

| Concern | Choice | Reason |
|---|---|---|
| Runtime | Node + TypeScript, in `pipeline/` | Same language as app, no context switch. |
| PDF extraction | `unpdf` | Page-aware, works in Node, no native deps. |
| Embeddings | `text-embedding-3-small` | Cheap; good enough for ~6 PDFs of retrieval. |
| LLM | Configurable (default `gpt-4o-mini` for generation, `gpt-4o` for verification critic) | Two-model setup keeps costs low while raising correctness. |
| Vector store | Local JSON file under `pipeline/index/2024/` | ~6 PDFs; no DB warranted. |
| Schema | Zod | Every LLM output validated; invalid output retried then rejected. |
| Determinism | `temperature: 0`, pinned model versions, hashed inputs, recorded in `provenance.json` | Reproducibility for audit. |

Bundle budgets (revised with realistic numbers):

- `/` ≤ 150KB gzipped JS
- `/survey` ≤ 200KB gzipped JS (Framer Motion lazy-loaded)
- `/results` ≤ 220KB gzipped JS (includes the small SVG chart)

CI fails if any route exceeds these.

## Core Domain Model

The runtime reads a single TypeScript file, **generated by the pipeline**:

```ts
// src/data/manifestos/2024.ts  (generated; do not hand-edit)

export type PartyId =
  | "labour" | "conservative" | "libdem"
  | "green" | "reform" | "snp";

export type TopicId =
  | "nhs" | "economy" | "education" | "housing" | "immigration"
  | "environment" | "crime" | "foreign" | "welfare" | "transport" | "democracy";

export interface Party {
  id: PartyId;
  name: string;
  shortName: string;
  colour: string;          // brand hex; contrast-checked in CI
  manifestoUrl: string;    // canonical PDF URL (used for #page=N deep links)
}

export interface Topic {
  id: TopicId;
  label: string;
  blurb: string;
  icon: string;
}

/** A party's position on a single statement. */
export interface Citation {
  quote: string;          // verbatim substring of the *normalised* source text
  printedPage: number;    // page as printed in the manifesto (shown to user)
  pdfPage: number;        // physical PDF page (used for #page=N deep links)
}

export type Stance =
  | {
      kind: "stated";
      score: -2 | -1 | 0 | 1 | 2;
      citations: Citation[];   // 1..3 supporting quotes from the same party's manifesto
      confidence: number;      // 0..1, from the pipeline; runtime informational only
    }
  | {
      kind: "unstated";
      note?: string;        // e.g. "Manifesto does not address this topic."
    };

export interface Statement {
  id: string;               // stable, human-curated (NOT LLM-generated), e.g. "nhs-funding-above-inflation"
  topic: TopicId;
  text: string;             // operationally testable: a specific policy proposition,
                            // present-tense, single-claim, ≤ 20 words, no vague modifiers
                            // ("significantly", "more", "better", "properly")
  stances: Record<PartyId, Stance>;
}

export const PARTIES: Record<PartyId, Party>;
export const TOPICS:  Record<TopicId, Topic>;
export const STATEMENTS: Statement[];   // ~3 per topic → ~33 total
```

A sibling `2024.provenance.json` records model versions, prompt hashes, source-PDF hashes, and run date. Both files are committed.

### Why `"unstated"` is a first-class variant

Manifestos are silent on many things. Coercing silence to `score: 0` would systematically bias matches toward parties with shorter or vaguer manifestos and force the pipeline to fabricate scores. The `unstated` variant lets the pipeline say "I have no evidence" honestly, lets the scoring exclude that pair from the per-party denominator, and lets the UI surface it as a feature rather than hide it.

### Election-cycle agnostic

`src/data/index.ts` re-exports the active manifesto:

```ts
export { PARTIES, TOPICS, STATEMENTS } from "./manifestos/2024";
```

Switching to 2029 is a one-line change after the pipeline produces `2029.ts`.

## Scoring Algorithm (Revised)

Per party $p$, let $Q_p$ be the set of questions where the user answered **and** party $p$ has a `stated` stance.

$$
\text{match}_p = \frac{\sum_{q \in Q_p} w_{t(q)} \cdot \bigl(4 - |a_q - s_{p,q}|\bigr)}{\sum_{q \in Q_p} 4 \cdot w_{t(q)}} \times 100
$$

- $a_q \in \{-2,\ldots,2\}$ — user answer.
- $s_{p,q}$ — party stance (only defined when `kind === "stated"`).
- $w_{t(q)} \in \{1, 2, 3\}$ — user-chosen topic importance (Low/Medium/High). Exposed as `IMPORTANCE_WEIGHTS = [1, 2, 3]` so the editorial choice is one line to tune. Rationale (max 3× swing — meaningful without overwhelming) documented on `/about`.

The denominator is **per-party** because $Q_p$ varies with how many statements that party stated a position on. A party that addressed only half the survey is scored against only the half it addressed; the results page surfaces "answered N of M statements" alongside each party's match so users can judge confidence.

Pure function in `src/lib/scoring.ts`, table-driven Vitest cases:

- Perfect agreement → 100%, perfect disagreement → 0%, all-neutral → 50%.
- Skipped questions excluded.
- Unstated stances excluded (exercised asymmetrically per party).
- Importance weights at extremes.
- Edge case: $|Q_p| = 0$ → return `null` (UI shows "Not enough overlap to score").

## User Flow

```
Landing  ──▶  Topic-importance picker  ──▶  Survey (one statement per screen)  ──▶  Results
                                                  │
                                                  └─ progress bar, back/skip, autosave
```

1. **Landing** — Hero, single primary CTA, 3-step "how it works", FAQ, footer with sources.
2. **Importance picker** — 11 topic chips; tap to mark Low/Medium/High (default Medium). One screen.
3. **Survey** — One statement per screen, 5 buttons (Strongly Disagree → Strongly Agree) + Skip. Animated slide. Progress bar. Autosaves.
4. **Results** — Ranked horizontal bar chart in party brand colours, with "answered N of M statements" beside each party's match (so users can judge confidence on parties with many `unstated` positions). Below: per-topic breakdown of top-match-per-topic, expandable to show the statements + each party's stance + verbatim quote(s) + manifesto-page link. Banner reiterates the GB-only scope. CTA → `/parties`.

The **GB-only scope is surfaced upfront** — on the landing page near the CTA and again on the importance-picker screen — so Welsh and NI users learn the limitation before investing 5 minutes.

### Smoothness details

- Keyboard: `1`–`5` answer, `←` back, `→` skip, `Enter` advance.
- Framer Motion `AnimatePresence` slide; respects `prefers-reduced-motion`.
- Autosave to `localStorage` after every answer via a safe-storage wrapper that no-ops in private mode and falls back to `sessionStorage` then in-memory. Refresh resumes mid-survey.
- **Hydration-safe**: survey/results are client components; the Zustand store uses `skipHydration: true` and rehydrates inside a `useEffect` to avoid React 19 SSR mismatches.

## Build-time Pipeline

The pipeline lives in `pipeline/` and is the only place LLMs are used. Its output is a committed `2024.ts` that the runtime trusts. Every stage is reproducible and inspectable.

```
┌──────────┐  ┌──────────┐  ┌────────────┐  ┌──────────┐  ┌──────────┐  ┌─────────┐  ┌────────┐
│ 1.Ingest │─▶│ 2.Index  │─▶│ 3.Generate │─▶│ 4.Score  │─▶│ 5.Verify │─▶│ 6.Review│─▶│ 7.Emit │
└──────────┘  └──────────┘  └────────────┘  └──────────┘  └──────────┘  └─────────┘  └────────┘
   PDFs        embeddings    statements      stances        citation +    human         2024.ts
               + page map    per topic       per party      neutrality    gate          + .provenance.json
                                                            checks        (REVIEW.md)
```

### 1. Ingest

- Download each manifesto PDF to `pipeline/sources/2024/<party>.pdf`. Hash and record in `provenance.json`.
- Extract text with `unpdf`, preserving PDF page numbers. Output `<party>.txt` plus `<party>.pages.json` mapping character offsets → PDF page.
- **Page-offset calibration recipe** (one-off, ~30 minutes total for six manifestos): for each manifesto, open the PDF, find the first page that has a printed page number, and record `{pageOffset: pdfPage - printedPage}` in a hand-written `pipeline/sources/2024/<party>.meta.json`. If a manifesto restarts numbering mid-document (rare), record an array of `{fromPdfPage, offset}` entries instead. The pipeline reads this; the emitted `Citation` carries both `pdfPage` (for `#page=N` deep links) and `printedPage` (shown to the user).
- Apply the `normalise()` function from stage 5 to the extracted text *once* and store the normalised form alongside the raw form. All downstream stages match against the normalised text.

### 2. Index

- Chunk by paragraph (with overlap) — typically 200–400 chunks per manifesto.
- Embed each chunk; store `pipeline/index/2024/<party>.json` as `[{text, page, embedding}]`. No external vector DB.

### 3. Statement generation (per topic)

- **Statement IDs are human-curated, not LLM-generated.** A committed `pipeline/statements/2024.seed.json` lists `{id, topic}` per planned statement (~3 per topic). The pipeline only fills in the `text`. This keeps overrides stable across re-runs (see finding on override stability).
- For each topic, retrieve top-K chunks from **all six parties** for the topic's seed query (e.g. "NHS funding, staffing, waiting times, social care").
- Prompt an LLM with those chunks plus a strict **operationally-testable rubric**:
  - A specific, falsifiable policy proposition (not a values statement).
  - Present tense, single claim, ≤ 20 words.
  - No vague modifiers (*significantly*, *more*, *better*, *properly*, *adequate*).
  - No loaded adjectives, no double negatives.
  - The six parties' positions on this statement must be distinguishable from their manifesto text.
- Output validated by Zod. A critic pass scores each statement on the rubric; statements below threshold are regenerated up to N times then flagged for human authoring.

### 4. Stance scoring (per statement × per party)

- For each `(statement, party)` pair, retrieve that party's top chunks for the statement.
- Prompt the LLM to return one of:
  ```json
  {
    "kind": "stated",
    "score": -2..2,
    "citations": [{ "chunk_index": <int>, "quote": "..." }, ...],   // 1..3 entries
    "confidence": 0..1
  }
  ```
  or
  ```json
  { "kind": "unstated", "note": "..." }
  ```
  `chunk_index` is an index into the *retrieved chunks* — the LLM **selects**, it does not invent page numbers. The pipeline maps each chosen chunk back to its real page via the page map from stage 1. Allowing up to 3 citations per stance reflects the reality that a party's position is often spread across an intro paragraph, a bullet list, and a costing line.
- Zod-validated; malformed output retried then dropped (becomes `unstated`).

### 5. Verify

Mechanical checks, plus one targeted critic call:

- **Citation verification (mechanical, exact)**: define a single `normalise(text)` function — NFKC, fold ligatures (`ﬁ`→`fi`), strip soft hyphens, collapse all whitespace (including non-breaking spaces) to single spaces, normalise smart quotes/dashes. Apply to *both* the source text and the LLM-returned `quote`. Then require an **exact substring match** of the normalised forms. No fuzzy matching — if it doesn't match exactly after normalisation, the citation is rejected and the whole stance becomes `unstated`. Unit-tested per artefact class (NBSP, soft hyphen, ligature, smart quote, line-break hyphen).
- **Page integrity**: `pdfPage` is taken from the page map of the chunk the LLM selected; `printedPage = pdfPage - pageOffset` from the manifesto's `<party>.meta.json`. The LLM never writes a page number.
- **Score sanity (critic)**: a second model is given the **statement and the quote(s)** (not the topic, not other chunks) and asked the same -2..+2 question the generator answered. Disagreement > 1 step flags the stance for human review. Same task framing as the generator means disagreement points at genuine ambiguity or error, not at context starvation.

CI fails the build if any pipeline output ships without passing the mechanical checks.

### 6. Human review gate

- `pipeline/overrides/2024.json` is the **canonical edit surface** for human decisions — a structured JSON file keyed by `(statementId, partyId)`. Reviewers edit this file directly (or via a small `pnpm review` CLI added later); it survives pipeline re-runs.
- `pipeline/REVIEW.md` is a **generated, human-readable summary** of items needing attention. Never edited by hand. Regenerated every pipeline run from the diff between current pipeline output and existing overrides.
- Items surfaced for review:
  - Every stance with `confidence < 0.7`.
  - Every stance flagged by the critic (score disagreement > 1).
  - Every statement that needed >1 regeneration to pass the rubric critic.
  - Any `(statementId, partyId)` whose pipeline output disagrees with an existing override (so reviewers can re-confirm or update).
- Override stability: because statement IDs are human-curated (stage 3) and party IDs are fixed, overrides cannot be orphaned by a pipeline re-run. A unit test ("override stability") asserts that re-running the pipeline against fixed inputs and a fixed seed produces identical `(statementId, partyId)` keys.
- Hard gate: emission (stage 7) refuses to run while `REVIEW.md` has unresolved items.
- Recommended process: two-person review for any change to `overrides/2024.json` (enforced via PR template + `CODEOWNERS`).

### 7. Emit

- Combine pipeline output + human overrides → write `src/data/manifestos/2024.ts`.
- Write `src/data/manifestos/2024.provenance.json`: model versions, prompt hashes, PDF hashes, run timestamp, **and a per-stance source map** `[{statementId, partyId, source: "pipeline" | "override", reviewer?: string, decisionDate?: string}]` so any stance's origin can be answered without crawling git history.
- Both files committed.

### Pipeline correctness gate (one-time spike)

Before relying on the pipeline, run a single-topic spike (NHS) end-to-end. Manually grade the resulting 3 statements × 6 stances. **Targets:**

- ≥ 95% of citations pass mechanical verification.
- ≥ 90% of stances rated "correct or defensibly close" by a human reviewer.

**Fallback mode if the spike fails**: same pipeline, same files, one config change — set the review threshold to `confidence < 1.0` so *every* stance is routed through `REVIEW.md`. `overrides/2024.json` becomes the primary data source; pipeline output is treated as draft suggestions. No code changes, no schema changes, no runtime impact.

### Pre-spike validation (cheap, do before writing pipeline code)

1. **PDF normalisation spike** — extract text from all six 2024 PDFs with `unpdf`; for each, hand-pick a known short quote from the source PDF and confirm it appears as a substring of the *normalised* extracted text. If any fails, the `normalise()` function needs revision before any pipeline work begins.
2. **Page-offset survey** — record `pageOffset` for each of the six manifestos by hand (~30 min total). De-risks stage 1 entirely.
3. **Statement-style pilot** — hand-write 5 statements in the operationally-testable style and run only stage 4 against the six manifestos. Manually grade. Isolates stance-scoring quality from statement-generation quality.

## Security, Privacy, Compliance

- **CSP**: nonce-based via Next middleware. `script-src 'self' 'nonce-…'`, `style-src 'self' 'nonce-…'`. Recent Framer Motion versions emit only nonce-able inline styles, but `next/font`'s injected `<style>` tags also need the nonce — verify in a pre-implementation spike that the request nonce flows to `next/font` styles in the pinned Next 15 version, plus a CI smoke test that scrapes rendered HTML for any unnonced `<style>` tag. If the spike fails, fall back to `style-src 'self' 'unsafe-inline'` and document the trade-off in `next.config.ts`.
- **No third-party trackers, no cookies.** Privacy notice on `/about`: only `localStorage`, nothing leaves the device. No cookie banner required.
- **Storage failures** handled by `safeStorage.ts` (try/catch + `sessionStorage` fallback + in-memory final fallback).
- **Electoral compliance** (UK):
  - Results phrased as *"your views align most with…"*, never *"vote for…"*.
  - `/about` states the tool is informational and non-partisan, names the data sources and the generation method, and provides a contact for corrections.
  - Imprint requirement: legal review before launch; if applicable, render the imprint in the footer. Out of scope to decide here, in scope to flag.

## Testing

- **Unit (Vitest)**:
  - `scoring.ts` — table-driven, including asymmetric per-party `Q_p`.
  - Manifesto Zod schema validation, applied to both real data *and* `__fixture__.ts` (so fixture drift is caught immediately).

- **Component (Vitest + Testing Library)**: `QuestionCard` keyboard handling; `ImportancePicker` state.
- **E2E (Playwright + axe-core)**: complete the survey with canned answers against `__fixture__.ts` → assert deterministic top party. axe-core a11y assertions on at least `/` and `/survey` (Lighthouse alone misses real issues).

- **Lighthouse budget** in CI: Performance ≥ 95, Accessibility = 100 on `/` and `/survey`.

**Phase 4 — Polish.**
`/parties` audit page with PDF deep-links, dark-mode tuning, Lighthouse tuning, legal review.

## Considerations & Trade-offs

- **LLM at build-time only** keeps the runtime trustworthy and the bundle small; concentrates risk into a process that has a human gate.
- **Two-model pipeline** (cheap generator + expensive critic) balances cost and correctness. Tunable.
- **`unstated` as first-class** is intellectually honest; slightly more complex UI ("answered N of M") and per-party denominator; clearly worth it.
- **Bundle budgets revised upward** to reflect Framer Motion's real cost; chart hand-rolled to keep things tight.
- **Static export kept as a secondary, CI-verified target** so we don't paint ourselves into a corner.
- **Big 6 only** in v1 (Plaid + NI parties absent). The data model handles their addition by extending `PartyId`; no scoring change. Banner on results acknowledges the gap.
- **Importance weights `[1, 2, 3]`** chosen for a max 3× swing — meaningful without overwhelming. Exposed as a constant for easy tuning; pinned by tests.

## Open Questions

1. **Override authority** — Who is the named human reviewer for `overrides/2024.json`? Two-person review enforced via PR template + `CODEOWNERS` is the recommended default.
2. **Legal/electoral review** — Who runs the pre-launch legal pass on wording and imprint? Needs a name, not a process.
3. **Domain & branding** — Final site name and domain. "WhoToVoteFor" is the working title.
4. **Pipeline budget** — Approximate token cost per full re-run is small (~$5–15 with the chosen models), but the spike should confirm. Also worth piloting `gpt-4o` (not just `gpt-4o-mini`) as the generator in the spike and picking based on review-load, not raw cost.
5. **Importance-weight UX** — Three-band Low/Medium/High invites users to mark everything "High", flattening weighting. Worth a post-launch experiment with a budget ("pick your top 3 priorities"); not a v1 blocker.
